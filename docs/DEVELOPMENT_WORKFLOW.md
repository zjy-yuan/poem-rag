# 开发流程与工程约定

> 项目：Poem RAG  
> 文档状态：v0.1  
> 创建日期：2026-09-19  
> 目标：用可执行的流程控制范围、契约、数据、质量和交付风险

## 1. 工程原则

1. **纵向切片优先**：每个阶段都交付一条可运行、可验证的用户路径。
2. **契约先行**：接口设计和错误语义先确认，再分别实现前后端。
3. **数据库迁移唯一**：所有结构变化通过 Alembic，不手改开发库后“补迁移”。
4. **业务规则在后端**：前端路由守卫只负责体验，最终权限和资源所有权由后端校验。
5. **测试靠近风险**：权限、事务、状态机、迁移和 RAG 检索必须有自动化验证。
6. **AI 改动必须评估**：模型、切块、检索、重排和 Prompt 改动不能只凭一次演示判定效果。
7. **失败可恢复**：异步任务、模型调用和外部依赖必须有超时、重试边界和明确错误码。
8. **小步交付**：一次只处理一个主题，不把重构、功能、格式化和依赖升级混在一起。
9. **文档随代码同步**：接口变化更新契约，功能完成更新项目说明，过程结论追加开发日志。
10. **先解决阻塞再扩范围**：环境或依赖连续失败时先记录并定位，不通过跳过测试掩盖问题。

## 2. 标准开发流程

### 阶段 0：需求澄清

开始编码前回答：

1. 哪个用户要完成什么任务？
2. 当前为什么做不到，现有能力缺在哪？
3. 本次包含什么，不包含什么？
4. 至少一条可以人工演示的验收路径是什么？
5. 是否涉及数据迁移、权限、费用、隐私或外部站点规范？

产物：任务目标、范围、非目标、验收标准。

### 阶段 1：影响面分析

从以下边界逐项检查：

| 边界 | 需要确认 |
| --- | --- |
| 前端 | 页面、路由、状态、加载、空态、错误、权限展示 |
| API | 路径、方法、参数、Schema、错误码、状态码、幂等 |
| 后端 | Router、Dependency、Service、事务、Repository |
| 数据库 | 表、关系、索引、约束、迁移、历史数据兼容 |
| Redis | 缓存键、过期、失效、限流、队列和一致性 |
| RAG | 语料、切块、Embedding、向量库、检索、重排、Prompt |
| 安全 | 身份、角色、资源所有权、输入边界、敏感数据 |
| 运维 | 配置、日志、指标、任务状态、失败重试、回滚 |

达到功能设计门槛时，先写 `docs/features/<feature>.md`。存在难以逆转的技术选择时，再写 ADR，并链接到功能设计文档。

### 阶段 2：更新接口契约

任何 API 改动先更新 `docs/FRONTEND_BACKEND_CONTRACT.md`，至少包含：

1. 业务目的和调用时机。
2. `METHOD /api/v1/...`。
3. 鉴权和角色要求。
4. 查询参数、路径参数和请求体。
5. 成功响应、分页或流式事件。
6. 可出现的错误码和 HTTP 状态码。
7. 幂等、并发、超时和重试语义。
8. 一个最小请求和响应示例。

实现完成后，以 OpenAPI 检查实际 Schema。两者不一致时，先修复差异再继续下一功能。

### 阶段 3：设计数据变化

先写迁移，再依赖迁移完成业务编码：

1. 明确事实来源和生命周期。
2. 明确主键、外键、唯一约束和删除策略。
3. 为真实查询设计索引，不为“可能有用”滥加索引。
4. 可空性和默认值必须兼容已有数据。
5. 迁移必须在空库和已有数据上都能执行。
6. 明确回滚策略；不可逆数据迁移需要单独说明。
7. 种子数据必须幂等，不能在每次启动时重复写入。

### 阶段 4：后端实现

推荐顺序：

```text
Pydantic Schema
  -> Repository
  -> Service 与事务
  -> API Router 与 Dependency
  -> 错误码和日志
  -> 自动化测试
```

后端完成标准：

1. 所有返回通过统一响应 Envelope，规定的 `204`、文件或 SSE 除外。
2. 权限在后端执行，资源查询带所有权或角色约束。
3. 业务状态变化集中在线 Service，不散落在 Router。
4. 数据库操作有明确事务边界，异常会回滚。
5. 关键失败能通过 Request ID、日志和稳定错误码定位。
6. 有正常路径、边界路径和拒绝路径测试。

### 阶段 5：前端实现

推荐顺序：

```text
API 模块
  -> 类型定义
  -> Store 或组合式状态
  -> 页面和组件
  -> 路由与权限展示
  -> 测试与构建
```

前端完成标准：

1. 页面不直接拼 URL，统一经过 `src/api`。
2. 请求类型与契约字段一致，字段保持 `snake_case`。
3. 加载、空数据、失败和无权限状态都有明确表现。
4. 权限页面只做体验层保护，提交后仍处理后端 `403`。
5. 移动端和桌面端均无文本溢出、遮挡和不可操作区域。
6. 类型检查、单元测试和生产构建通过。

### 阶段 6：联调与验收

1. 使用真实 MySQL 和 Redis 运行迁移、种子和服务。
2. 按验收路径完成一次真实请求，不只依赖 Mock。
3. 验证成功、校验失败、无权限、资源不存在和依赖不可用。
4. 前端执行完整用户路径，检查刷新、返回和重复提交。
5. 长任务或流式接口检查断线、超时和重试。
6. 记录实际命令、结果和未覆盖项。

### 阶段 7：收尾

1. 更新 `PROJECT_GUIDE.md` 中的当前能力和代码导览。
2. 更新 `FRONTEND_BACKEND_CONTRACT.md` 的接口变更记录。
3. 在 `DEVELOPMENT_LOG.md` 追加目标、决策、完成内容、验证和风险。
4. 确认没有把 `.env`、密钥、日志样本或真实用户数据纳入版本管理。
5. 将未完成内容写入“下一步”，不只留在聊天记录中。

## 3. 接口变更检查表

新增或修改接口时必须确认：

- 路径使用复数资源名，动作型需求优先映射为资源状态变化。
- 路径、查询、请求和响应字段统一使用 `snake_case`。
- 列表接口分页参数和 `meta` 保持一致。
- 创建返回 `201`，普通查询和更新返回 `200`，无响应体删除可返回 `204`。
- 鉴权失败返回 `401`，已登录但无权限返回 `403`，资源不存在返回 `404`。
- 前端只依赖稳定错误码，不根据中文错误消息做业务分支。
- 并发更新有版本号或等价机制，重试不会产生重复资源。
- 接口变更追加到契约的“接口变更记录”。
- 破坏性变更必须提供迁移窗口或新版本路径，不能无提示直接替换。

## 4. 数据库变更检查表

- ORM 模型、迁移和真实数据库结构三者一致。
- `upgrade` 和 `downgrade` 均已审阅。
- 唯一约束和并发写入路径经过验证。
- 删除策略明确区分硬删除、软删除、归档和级联。
- 时间统一保存 UTC，接口按契约返回 ISO 8601。
- 新索引有对应查询场景，外键列有合理索引。
- 数据修复脚本可重复执行。
- 迁移后执行后端测试并完成至少一次真实数据库查询。

## 5. RAG 变更检查表

每次改变以下任一项，都视为一次 RAG 实验：

1. 语料范围或数据版本。
2. 正文清洗、规范化或去重规则。
3. 切块单位和重叠策略。
4. Embedding 模型、维度或归一化方式。
5. 向量库集合、过滤字段或索引参数。
6. BM25、Dense、混合检索、RRF 或 Reranker 配置。
7. 查询改写、上下文组装、Prompt 和生成模型。
8. 引用校验、拒答或输出解析规则。

实验记录至少包含：

```text
实验编号
代码版本
语料版本
评估集版本
关键配置
Recall@k / MRR / 引用准确率 / 忠实度
P95 延迟 / 平均 Token / 单次成本
失败样例
结论：保留、回退或继续实验
```

没有基线、评估集或失败样例对比时，不把“感觉更准”写成优化成果。

## 6. 完成定义（Definition of Done）

一个功能只有同时满足以下条件才算完成：

1. 验收路径在真实运行环境中通过。
2. 接口契约、OpenAPI 和前端调用一致。
3. 数据库迁移已经执行且可重复部署。
4. 正常、边界、失败和权限路径有测试或明确人工验收记录。
5. 日志不泄露密钥，错误可以定位。
6. 文档与代码同步，开发日志包含验证结果。
7. 已知风险和未覆盖范围被明确记录。

## 7. 阻塞处理规则

出现环境、服务或第三方依赖失败时：

1. 保存原始命令、完整错误和已尝试方案。
2. 先做最小可验证检查，例如端口、进程、配置、网络和权限。
3. 同一原因连续尝试 3 次仍失败时停止盲目重试。
4. 改为记录“阻塞点、验证证据、可选方案、需要用户配合的动作”。
5. 阻塞不牵涉核心路径时，可先推进不依赖它的模块，但不能宣称整条流程已验收。

典型需要用户配合的场景：

- MySQL/Redis 服务无法启动或本地凭据不正确。
- 需要登录第三方模型平台、充值额度或配置 API Key。
- 需要确认目标网站条款、robots、版权或抓取范围。
- 需要云服务器、域名、DNS、证书或实名相关操作。

## 8. 文档维护节奏

| 时点 | 动作 |
| --- | --- |
| 功能开始 | 写功能设计，更新契约草案 |
| 数据库变化 | 更新迁移说明和项目导览 |
| 接口实现完成 | 核对 OpenAPI 和契约 |
| 前后端联调完成 | 更新项目说明中的“当前能力” |
| 阶段结束 | 追加开发日志并写明下一步 |

文档的目标是降低返工和沟通成本。任何新增模板、状态或审批环节，如果不能减少实际风险，就不应加入流程。

## 9. 环境与发布流程

环境按用途分离，不能把本地开发习惯直接带到生产：

| 环境 | 用途 | 数据与配置要求 |
| --- | --- | --- |
| 本地开发 | 快速编码、迁移试验、真实联调 | 使用本机 `.env`，不提交密钥 |
| CI/测试 | 每次变更自动验证 | 无真实用户数据，依赖用隔离或容器服务 |
| 预发布可选 | 部署验收、演示、兼容性检查 | 配置接近生产，使用测试数据 |
| 生产 | 作品集访问或真实服务 | 独立密钥、备份、TLS、监控和最小权限 |

发布顺序：

```text
冻结本次范围
  -> 全部门禁通过
  -> 审阅迁移和回滚
  -> 部署依赖与服务
  -> 执行迁移
  -> 健康检查和核心路径烟测
  -> 观察日志、错误率和延迟
  -> 记录版本、结果和回滚点
```

发布要求：

1. 代码版本、数据库迁移版本、模型配置和 Prompt 版本可以对应。
2. 生产环境禁止开发管理员种子和调试错误详情。
3. 密钥通过部署环境注入，不写入镜像、仓库或前端构建产物。
4. 数据库迁移前有备份或可验证恢复方案。
5. 新版本失败时能回退应用版本，并明确数据库是否允许回滚。
6. 域名、HTTPS、DNS 和证书属于部署阶段任务，不抢占当前 RAG 核心开发时间。

## 10. CI 质量门禁

本地统一入口：

```powershell
.\scripts\verify.ps1
```

该脚本执行 Ruff、后端测试、前端类型检查、Vitest 和生产构建。GitHub Actions 使用
等价的后端与前端 job，在每次 push 和 pull request 时执行基础门禁，不连接真实模型、
MySQL、Redis 或 Qdrant。

当前必须包含的基础检查：

```powershell
.\.venv\Scripts\python.exe -m ruff check apps\api
.\.venv\Scripts\python.exe -m pytest -q
pnpm --dir apps\web typecheck
pnpm --dir apps\web test
pnpm --dir apps\web build
```

后续进入数据库和 RAG 阶段后增加：

1. Alembic 从空库升级到 head 的测试。
2. 迁移重复执行和种子幂等测试。
3. OpenAPI 生成成功及前后端类型同步检查。
4. 关键 API 契约测试和浏览器 E2E。
5. 固定语料与固定评估集的检索回归。
6. 密钥扫描、依赖漏洞和容器镜像检查。

CI 失败即该变更未完成，不能靠人工忽略失败继续累积下一批改动。对于暂时无法自动化的评估，必须在开发日志中记录手工命令、数据版本和结果。

## 11. ADR 使用规则

出现以下选择时创建 ADR，并使用 `docs/adr/ADR-XXX-short-title.md`：

1. 修改整体架构或模块边界。
2. 更换数据库、向量库、任务系统或主要框架。
3. 修改数据事实来源、权限模型或一致性策略。
4. 更换 Embedding、生成模型、检索基线或评估标准。
5. 引入微服务、消息系统、知识图谱等大范围能力。

ADR 至少包含：背景、候选方案、决策、原因、影响、回滚条件和复查时间。普通 API 和页面设计留在功能设计文档中，不为每个小改动写 ADR。
