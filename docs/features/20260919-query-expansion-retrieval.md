# 查询改写与多查询 RRF 检索

> 状态：已实现（内部 Service 与离线评估入口）  
> 创建日期：2026-09-19  
> 最近更新：2026-09-20
> 关联任务：修复现代自然语言到诗词领域词的召回失败，同时保留词法基线的精确匹配能力

## 1. 背景与问题

固定评估集 `lexical-baseline-seed-v1` 暴露了三条明确失败：

1. `李白写月亮的诗句`
2. `苏轼关于中秋的词`
3. `表达思乡情绪的诗句`

当前 `lexical-baseline-v1` 只把原查询作为 `LIKE` 条件，无法把“月亮”连接到“明月”、
把“想家”连接到“思乡/故乡”，也无法把自然语言问题稳定转换成作者过滤条件。直接等待
Dense 检索会掩盖查询理解本身的问题，也无法说明失败来自召回、向量化还是排序。

因此先建立一个不依赖外部模型的查询理解基线：用可审查的诗词词典改写查询，再对多个
改写结果分别召回，最后用 RRF 融合排名。这样可以先证明“查询改写是否有效”，再与
Dense、Hybrid 和 Rerank 做同集对比。

## 2. 目标

1. 定义 `QueryRewrite` 和 `QueryRewriter` 边界，允许后续替换为 LLM 或数据库词典。
2. 实现确定性的 `LexiconQueryRewriter`，覆盖月亮、思乡、元宵、怀人和已知作者实体。
3. 保留原查询，不把改写结果替换成用户输入。
4. 新增 `expanded-lexical-v1` 内部检索策略，对原查询和改写变体分别召回。
5. 使用 RRF 按排名融合，避免比较不同查询产生的异构规则分数。
6. 在相同 27 条评估集上与 `lexical-baseline-v1` 比较，不修改公开 HTTP 接口。
7. 输出 `query_expansion` 和 `rrf_fusion` 匹配标记，便于分析命中来源。

## 3. 非目标

1. 不调用 LLM 做查询改写，不把未验证的模型输出直接作为检索条件。
2. 不实现同义词库的数据库管理和后台审核界面。
3. 不接入 Qdrant、Qwen Embedding、Sparse/BM25 或 Cross-Encoder Rerank。
4. 不切换 `GET /api/v1/search/evidence` 的公开策略。
5. 不宣称当前规则覆盖开放语料中的全部意象、典故和别名。
6. 不把 `expanded-lexical-v1` 的 RRF 分数解释为最终相关性概率。

## 4. 用户场景与验收标准

| 场景 | 操作 | 预期结果 |
| --- | --- | --- |
| 现代月亮表达 | 查询“李白写月亮的诗句” | 召回《静夜思》，并标记 `query_expansion` |
| 中秋词查询 | 查询“苏轼关于中秋的词” | 召回《水调歌头·明月几时有》 |
| 情绪查询 | 查询“表达思乡情绪的诗句” | 召回包含“思乡/故乡/天涯”的诗句 |
| 精确引用 | 查询完整诗句 | 仍优先返回完全匹配 chunk |
| 无答案 | 查询“量子纠缠的物理实验” | 不因扩展词误召回诗词 |
| 空查询 | 查询仅含空白 | 返回 `422 VALIDATION_ERROR`，不调用检索 |
| 过滤透传 | 请求粒度、作者或朝代过滤 | 原样传给每次子查询 |
| 契约兼容 | 策略输出证据 | 继续满足 `RetrievalEvidence`，分数在 `[0, 1]` |

## 5. 方案概览

```text
query
  -> 空值校验
  -> LexiconQueryRewriter
       -> 识别作者/朝代实体
       -> 识别 moon / homesickness / lantern_festival / longing 等领域概念
       -> 领域概念覆盖的字符不再重复触发朝代实体
       -> 生成去重后的查询变体
  -> 原查询 + 每个变体分别调用 RetrievalService
  -> 按 chunk_id 去重
  -> RRF: score += 1 / (60 + rank)
  -> 显式多证据查询限制单个作品最多 2 个候选槽位
  -> 按 RRF 分数、最佳源排名、chunk_id 排序
  -> 归一化并返回 RetrievalEvidence[]
```

关键取舍：

1. 规则词典先于模型改写，因为当前失败样本少、语义边界明确，规则可以完全复现和审查。
2. 只有查询包含诗词意图词时才应用概念扩展，避免把普通单字“月”误判为诗词查询。
3. 作者实体独立识别，使“李白写月亮的诗句”同时保留作者和意象约束。
4. 原查询始终参与召回，防止改写失败时丢失精确匹配能力。
5. 多查询融合使用 RRF，不直接相加每个子查询的规则分数。
6. 只有“两首、分别、各自、对比”等显式多证据问题才启用作品槽位限制，避免普通
   查询被过度约束。
7. 当前所有子查询顺序执行，因为复用同一个 `AsyncSession`；真实延迟需要后续评估。

## 6. 接口与契约

本切片不新增或修改公开 HTTP API。

内部策略：

| 字段 | 值 |
| --- | --- |
| `strategy` | `expanded-lexical-v1` |
| 改写器 | `LexiconQueryRewriter` |
| 融合方式 | Reciprocal Rank Fusion，`rank_constant=60` |
| 候选数量 | 每个变体取 `limit * 5`，最多 200 |
| 多证据候选 | 显式多证据查询时，每个作品最多先占 2 个槽位，再按 RRF 顺序补满 |
| 排序 | RRF 分数降序、最佳源排名升序、`chunk_id` 升序 |
| 匹配类型 | 合并子查询匹配类型，并追加 `query_expansion`、`rrf_fusion` |
| 分数范围 | 归一化到 `[0, 1]`，保留 6 位小数 |

命令行：

```powershell
.\.venv\Scripts\python.exe apps\api\scripts\evaluate_retrieval.py `
  --strategy expanded `
  --top-k 5
```

公开接口边界：

1. `/api/v1/search/evidence` 继续使用 `lexical-baseline-v1`。
2. `expanded-lexical-v1` 只供内部 Service、测试和离线评估使用。
3. 切换公开策略前必须完成真实语料、Dense、Hybrid 和查询改写的同集比较。

## 7. 数据设计

本切片不新增表或迁移。

词典当前以版本化 JSON 维护，文件为
`data/query_expansion/lexicon_v1.json`，版本标识为 `query-lexicon-v1`。
加载时会校验版本、概念名称、触发词、扩展词、实体和诗词意图词是否为空或重复；
`LexiconQueryRewriter` 默认读取该文件，也支持测试注入自定义词典。

概念规则包含：

| 概念 | 触发词 | 扩展词 |
| --- | --- | --- |
| `moon` | 月亮、月光、明月、中秋、赏月 | 明月、月光、中秋 |
| `homesickness` | 思乡、想家、故乡、乡愁、羁旅、游子 | 思乡、故乡、天涯 |
| `lantern_festival` | 元宵、元夕、元夜、上元、花灯、灯火、灯会 | 元夕、灯火、花灯 |
| `longing` | 怀人、怀念、思念、想念、牵挂 | 怀人、怀念、思念、子由、苏辙 |

已知实体覆盖当前种子作者和部分开放语料作者，例如李白、苏轼、李清照、辛弃疾等。
后续若需要在线运营和审核，再迁移到数据库表，并记录来源、启用状态、审批人和变更
审计；当前文件版本已经可以随代码和评估结果一起追踪，不引入额外迁移和管理界面。

## 10. RAG 与评估

真实 MySQL 同集对比：

| 策略 | 通过数 | 通过率 | Recall@5 | MRR | 平均延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `lexical-baseline-v1` | 24/27 | 0.888889 | 0.869565 | 0.869565 | 2.542 ms |
| `expanded-lexical-v1` | 27/27 | 1.000000 | 1.000000 | 0.978261 | 3.769 ms |

`expanded-lexical-v1` 分类结果：

| 分类 | 通过率 | Recall@5 | MRR |
| --- | ---: | ---: | ---: |
| 精确引用 | 1.000000 | 1.000000 | 1.000000 |
| 短语 | 1.000000 | 1.000000 | 1.000000 |
| 标题 | 1.000000 | 1.000000 | 1.000000 |
| 作者 | 1.000000 | 1.000000 | 1.000000 |
| 朝代 | 1.000000 | 1.000000 | 1.000000 |
| 多证据 | 1.000000 | 1.000000 | 1.000000 |
| 自然语言 | 1.000000 | 1.000000 | 0.833333 |
| 无答案 | 1.000000 | n/a | n/a |

结论：

1. 规则改写修复了三条自然语言失败，同时保持精确引用、短语、标题、作者、朝代和拒答通过。
2. 这是当前 6 首种子语料上的结果，不能外推为开放语料或生产环境准确率。
3. 平均延迟从 2.542 ms 增至 3.769 ms，主要来自多次词法查询；真实语料下需要重新测量。
4. Dense、Hybrid 和 Rerank 仍需在同一数据集上完成真实 Qdrant/Qwen 联调后比较。

开放语料复核（`open-corpus-100-v1`，50 条，Top-5）：

| 策略 | 通过 | Recall@5 | MRR | 平均延迟 |
| --- | ---: | ---: | ---: | ---: |
| `lexical-baseline-v1` | 36/50 | 0.678571 | 0.650794 | 16.482 ms |
| `expanded-lexical-v1` | 36/50 | 0.797619 | 0.722222 | 26.626 ms |

本轮补充元宵、怀人和“辛弃疾”后，自然语言从 3/9 提升到 4/9，长文本从 0/4 提升
到 1/4；词法基线未回归。该结果仍低于 `hybrid-rrf-v1 + 0.60` 的 47/50，且无答案
准确率只有 `0.375`，因此 `expanded-lexical-v1` 只作为在线问答的可解释召回分支，
拒答仍由 `assess` 负责。

1000 首独立 holdout 复核：

| 数据集 | 策略 | 通过 | Recall@5 | MRR | 无答案准确率 |
| --- | --- | ---: | ---: | ---: | ---: |
| `retrieval-holdout-1000-v1` | `expanded-lexical-v1` | 48/50 | 0.952381 | 0.880952 | 1.0 |
| `retrieval-holdout-1000-v2` | `expanded-lexical-v1` | 38/46 | 0.815789 | 0.763158 | 0.875 |

v2 首轮暴露了三类候选选择问题，已用通用规则修复，没有增加样本 ID 特例：

1. 结构化主题查询（作者 + 朝代 + 体裁 + 主题）被显式标题槽位挤掉正文证据。
   现在结构化主题查询在锚点之后保留一个 `poem`/`line` 主文本候选。
2. 多标题查询优先命中单行 chunk，完整作品块没有槽位。现在优先选择完整 `poem` 块。
3. 主文本候选的余弦分数略低于全局阈值时被整段过滤。现在 `poem`/`line` 允许
   `0.02` 容差，`note` 仍严格使用调用方阈值。

修复后同一 v2 数据集上在线组合从 40/46 提升到 45/46，同批生成 holdout 从 24/26
提升到 `26/26`。唯一剩余检索失败 `no-answer-v2-xinqiji-office-08` 由在线 `assess`
负责拒答。完整结果见 `20260924-independent-1000-holdout-v2.md`。

## 12. 风险与回滚

1. 规则词典可能对多义词、典故和同名作者产生误扩展。
2. 当前只覆盖四条概念规则和有限作者列表，不能代表真实诗词领域覆盖度。
3. 多个变体会增加数据库查询次数和延迟；高并发下需要缓存或批量查询优化。
4. RRF 等权融合尚未根据真实语料调参，可能放大低质量变体。
5. 无答案样本仍可能被宽泛扩展词误召回，扩展语料后必须扩大负样本集。
6. 回滚方式是停止使用 `ExpandedRetrievalService` 和 `--strategy expanded`，公开接口继续使用词法策略。
7. 元宵、怀人和多证据槽位来自 28 条生成 holdout 的失败修复，需要独立样本复核，
   避免把局部词典补丁误认为通用查询理解能力。
