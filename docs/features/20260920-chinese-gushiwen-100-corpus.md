## 1. 背景与问题

项目此前只有 6 首种子诗词。种子数据足以验证工程链路，但不能证明导入 Service、
结构切块和检索策略能处理真实开放语料。直接爬取整站又会同时引入来源漂移、字段清洗、
许可、去重和长尾文本问题，不利于先验证方法。

因此本轮选择固定版本、固定文件和小规模分层抽样，先回答以下问题：

1. 第三方 NDJSON 能否无损转换为现有 `CorpusImportDataset`。
2. 注释、译文和赏析能否进入现有版本与 chunk 模型。
3. 真实长文本能否完成结构切块、Qwen Embedding 和 Qdrant upsert。
4. 扩库后原有检索评估是否仍然成立，退化集中在哪里。
5. 在投入全量导入前，哪些数据治理和检索问题必须优先解决。

## 2. 目标

1. 不新增数据库迁移，复用现有来源、版本、注释、切块和索引能力。
2. 固定来源 commit 和原始文件 SHA256，保证转换输入可追溯。
3. 只导入 100 首，按朝代和正文长度分层抽样，覆盖短、中、长文本。
4. 保留 `remark`、`translation`、`shangxi`，分别映射为 `note`、`translation`、
   `appreciation`。
5. 将来源分类标记转换为 tags，不把标签硬编码为新的业务表。
6. 默认转换和导入为草稿；本次验证显式使用 `publish=true`。
7. 对导入、切块、向量化、检索和生成分别留下可复查报告或命令。
8. 记录许可风险，不把第三方注释、译文和赏析标记为 AI 生成。

## 3. 非目标

1. 不实现网站爬虫、站点适配器或增量同步。
2. 不导入全量 `chinese-poetry`、`PoetryLibrary` 或商业 API 数据。
3. 不实现跨来源作品合并、作者消歧和版本差异审核。
4. 不自动补写缺失的注释或赏析。
5. 不把 100 首样本结果外推为开放语料或生产准确率。
6. 本轮不切换在线问答检索策略，也不引入 Rerank。

## 5. 抽样与转换

输入共 1000 条，处理结果：

| 阶段 | 数量 |
| --- | ---: |
| 原始记录 | 1000 |
| 排除的非诗词记录 | 534 |
| 来源内重复候选 | 1 |
| 可参与抽样的唯一诗词 | 465 |
| 最终选中 | 100 |

抽样方法为 `dynasty_and_content_length_stratified_v1`：

1. 先按朝代分配至少 1 个名额，再按池大小和理想配额补足。
2. 每个朝代内轮转选择短、中、长文本，避免只抽短诗。
3. 内容长度小于 80 字符为 `short`，80 至 300 字符为 `medium`，超过 300 字符为
   `long`。

选中分布：

| 维度 | 分布 |
| --- | --- |
| 朝代 | 唐 37、宋 36、先秦 10、汉 4，其余 9 个朝代共 13 |
| 长度 | short 50、medium 40、long 10 |
| 注释 | 98 首 |
| 译文 | 100 首 |
| 赏析 | 97 首 |

字段映射：

| 来源字段 | 项目字段 | 说明 |
| --- | --- | --- |
| `_id.$oid` | `external_id` | 来源内稳定幂等键 |
| `title`、`writer` | `title`、`author_name` | 作者不存在时自动创建 |
| `dynasty` | `dynasty_name` | 规范化 `唐代 -> 唐` 等名称 |
| `content` | `content` | 保持原文换行和内容 |
| `type` | `tags` | 最多 30 个，不直接改变分类树 |
| `remark` | `note` 注释 | 第三方注释 |
| `translation` | `translation` 译文 | 第三方译文 |
| `shangxi` | `appreciation` 赏析 | 第三方赏析，不标记为 AI 生成 |

`raw_payload` 只保存来源文件、行号、来源 ID、原始朝代、作者、类型和可选音频 URL，
不复制整条第三方原始载荷。

## 6. 导入、切块与索引

当前闭环：

```text
固定 NDJSON
  -> convert_chinese_gushiwen.py
  -> CorpusImportDataset
  -> import_corpus.py --rebuild-chunks
  -> poem_sources / poem_versions / poem_annotations / poem_chunks
  -> index_chunks.py --all-pending
  -> Qwen text-embedding-v4
  -> Qdrant poem_chunks_v1
```

复现命令：

```powershell
.\.venv\Scripts\python.exe apps\api\scripts\convert_chinese_gushiwen.py `
  --input data\raw\chinese-gushiwen-guwen0-1000-c2345d0.json `
  --publish

.\.venv\Scripts\python.exe apps\api\scripts\import_corpus.py `
  --input data\import\generated\chinese-gushiwen-100-v1.json `
  --report data\import\reports\chinese-gushiwen-100-v1.import.json `
  --rebuild-chunks

.\.venv\Scripts\python.exe apps\api\scripts\index_chunks.py --all-pending
```

`--publish` 仅用于本次公开浏览和检索验证。转换器和导入契约的默认值仍是
`publish=false`，正式批量导入应先预检，再决定是否发布。

| 导入创建 | 100 |
| 更新 | 0 |
| 未变化 | 0 |

## 7. 评估结果

### 7.1 检索层

在原有 `retrieval_lexical_v2.json` 的 31 条样本、Top-5 和真实扩库环境上重跑：

| 策略 | 通过 | Recall@5 | MRR | 无答案准确率 | 平均延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `lexical-baseline-v1` | 28/31 | 0.869565 | 0.775362 | 1.000000 | 21.036 ms |
| `expanded-lexical-v1` | 25/31 | 0.869565 | 0.768116 | 0.625000 | 21.841 ms |
| `dense-baseline-v1` | 17/31 | 0.760870 | 0.718841 | 0.000000 | 217.912 ms |
| `dense-baseline-v1` + `0.22` | 18/31 | 0.760870 | 0.718841 | 0.125000 | 203.762 ms |
| `hybrid-rrf-v1` + `0.22` | 20/31 | 0.847826 | 0.834783 | 0.125000 | 202.499 ms |
| `hybrid-rrf-v1` + `0.50` | 23/31 | 0.847826 | 0.813043 | 0.500000 | 246.967 ms |

扩库前 `expanded-lexical-v1` 为 29/31、Hybrid + `0.50` 为 31/31。扩库后结果
明显退化，退化集中在自然语言问题、作者和朝代类查询，以及领域内无答案样本。
因此不能继续用扩库前的 `27/27` 或 `31/31` 证明当前检索策略有效，也不能通过调高
`min_score` 掩盖问题。

旧集只能说明扩库冲击，不能代表开放语料检索质量。随后已新增
`data/eval/retrieval_open_corpus_v1.json`（`open-corpus-100-v1`，50 条）并切换为
默认离线评估集。开放语料 Top-5 中，Hybrid + `0.60` 为 47/50、Recall@5
`0.988095`、可回答无结果率 0，但仍有 2 条领域内无答案漏拒。完整对照和失败类型见
[开放语料检索评估 v1](20260920-open-corpus-retrieval-evaluation.md)。

主要根因：

1. 原有 31 条金标准只覆盖 6 首种子作品，无法表达扩库后的候选歧义。
2. 本次导入与原种子存在内容重复但 ID 不同，精确查询可能同时返回两条作品。
3. 查询改写词典只覆盖少量作者、意象和主题，面对 100 首语料时触发不足。
4. Dense 单路无法区分“话题相关但答案属性缺失”的证据。
5. 现有评估集缺少开放语料版本，语料规模变化和策略变化没有完全解耦。

### 7.2 生成层

原有 12 条生成样本在扩库后仍为 `12/12`，但该集合只覆盖种子作品。随后新增了
`generation-rag-open-corpus-100-v1` 28 条独立 holdout，并切换为默认生成评估入口：

| 指标 | 结果 |
| --- | ---: |
| 通过 | 28/28 |
| 有答案准确率 | 1.000000 |
| 拒答准确率 | 1.000000 |
| 拒答 P/R/F1 | 1.000000 / 1.000000 / 1.000000 |
| 引用精确率 | 1.000000 |
| 引用召回率 | 1.000000 |
| 平均延迟 | 2087.159 ms |
| P95 延迟 | 4075.593 ms |

上一轮四条失败均为有答案问题被 `assess` 判为 `missing_fact`，集中在《青玉案·元夕》、
《琵琶行》、《孔雀东南飞》和多证据月亮问题。随后通过补充元宵/怀人概念、限制单个
作品的多证据候选槽位，以及按作品轮转长文本父级上下文完成修复，当前生成 holdout
达到 `28/28`。完整记录见
[开放语料生成层 holdout v1](20260920-open-corpus-generation-evaluation.md)。

## 10. 风险与后续

1. 当前 28 条 holdout 已达到 `28/28`，但样本仍小且经过针对性调参，必须增加独立
   holdout 后再评价泛化。
2. 设计跨来源作品去重与合并，消除种子作品和导入作品的 ID 歧义。
3. 为作者、朝代、体裁和标签增加结构化过滤，不只依赖词法或向量召回。
4. 引入 Rerank，并单独比较召回阶段和排序阶段的变化。
5. 为长诗、词和组诗制定 token 预算、父级上下文截断和分块策略。
6. 在开放语料评估稳定后，再决定是否扩大来源或提升 Embedding 维度。
7. 建立按来源删除、来源许可见证和公开部署免责声明。
